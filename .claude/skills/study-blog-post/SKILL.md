# 학습 노트 → 블로그 글

## 역할 분담

| 단계 | 하는 사람 | 산출물 |
|---|---|---|
| 1 개요 | AI | 제목 후보, 목차, 절마다 "무엇을 서술하라", 쓸 코드, 제외 소재 |
| 2 집필 | 사용자 | 본문 산문 |
| 3 검토 | AI | 사실 오류 지적, 문장·맞춤법 다듬기 |

**AI는 본문 산문을 쓰지 않는다.** 1단계 산출물은 지침과 코드까지다. 문단을 완성해서 주면 위반이다.

경계가 애매한 지시가 오면 개요 범위인지 되묻는다. 2026-08-23에 "나머지는 너가 알아서 채워줘"를 본문 집필 위임으로 읽고 11,600자를 대신 써버린 전례가 있다. 아래 표현은 모두 개요 범위로 읽고, 본문까지 원하면 사용자가 그렇게 말할 때만 쓴다.

- "나머지는 알아서" · "정리해줘" · "채워줘" · "제목은 N번으로"

## Phase 1 — 개요

### 읽을 것

1. **학습 노트** — 해당 주제 디렉터리의 `README.md`(확립된 사실 · 사다리 · 진행 규칙)와 `journal.md`(세션 로그 · 오개념 표 · 복습 큐). 글감은 여기서만 나온다.
2. **직전 글** — 이미 발행한 앞 편. 다룬 내용을 재설명하면 독자가 지친다. 발행본 URL이 있으면 읽고, 없으면 사용자에게 묻는다.
3. **글 놓을 자리** — Notion 페이지 URL 등. Phase 3에서 다시 읽어야 하니 개요와 함께 기록해 둔다.

### 스파인 하나를 정한다

두 단원 분량을 그냥 이어 붙이면 소재 나열이 된다. 독자가 따라올 축을 하나 세우고 소재를 그 축에 배치한다. 축이 안 서면 두 편으로 쪼갤 것을 제안한다.

축 후보를 고를 때 쓸 만한 형태:

- 대상이 바뀐다 — 앞 편이 A를 다뤘으면 이번 편은 B (예: 유니온 → 객체)
- 능력 순서 — 읽기 → 만들기 → 변환하기
- 목표 하나 — 표준 유틸리티를 직접 만들면서 필요한 도구를 순서대로 꺼낸다

### 개요 산출물

절마다 아래를 준다. 산문은 쓰지 않는다.

| 항목 | 내용 |
|---|---|
| 서술할 것 | 이 절에서 세울 주장 한두 줄. 문단이 아니라 지시문 |
| 쓸 코드 | 노트에서 검증된 코드 블록 그대로 |
| 회수 지점 | 앞 편이나 앞 절에서 세운 규칙 중 여기서 다시 쓰이는 것 |
| 강조할 한 문장 | 절의 결론. 사용자가 자기 문장으로 풀어 쓸 재료 |

전체 개요 끝에는 두 목록을 붙인다.

- **넣지 말 것** — 분량이 터지거나 곁길이 긴 소재. 이유와 함께
- **앞 편과 겹치는 것** — 재설명하지 말고 한 줄 참조로 넘길 항목

### 개요를 어디에 쓰나

기본은 대화에 출력한다. 사용자가 페이지에 골격을 넣어달라고 하면 제목·소제목과 절별 지침만 넣고 본문 자리는 비운다.

## Phase 2 — 사용자 집필

AI는 기다린다. 사용자가 일부만 쓰고 물어보면 그 절 범위에서만 답한다. "이 문단 어떻게 시작할까"에 문단을 써주지 않는다 — 재료(코드·주장·회수 지점)를 다시 제시한다.

## Phase 3 — 검토

사용자가 채운 글을 받으면 세 축으로 본다. **사실 검증이 먼저다.** 문장 다듬기부터 시작하면 틀린 내용이 매끄러워질 뿐이다.

### 1) 사실 오류

글에 실린 값·규칙·용어를 전부 검증한다. 근거는 실측이다.

```
npx -y -p typescript@5 tsc --strict --noEmit --target es2022 <file>
```

`Eq`/`Assert` 이디엄으로 값을 고정한다.

```ts
type Eq<X, Y> = (<T>() => T extends X ? 1 : 2) extends (<T>() => T extends Y ? 1 : 2) ? true : false;
type Assert<T extends true> = T;
```

에러 메시지를 인용하는 문장은 실제 컴파일러 출력과 대조한다. 기억으로 쓰지 않는다.

찾은 오류는 이렇게 보고한다. 고쳐 쓴 문장을 바로 들이밀지 않고 무엇이 틀렸는지부터 말한다.

- 원문 인용
- 무엇이 틀렸나
- 실측 출력
- 어떻게 고칠지 제안

**과잉일반화가 가장 흔한 오류 부류다.** 조건이 붙어야 하는 규칙을 무조건으로 쓴 문장. 규칙을 볼 때마다 "예외가 있나"를 실측으로 확인한다.

### 2) 용어

핸드북·공식 문서에 없는 용어를 쓰고 있으면 알린다. 출처가 컴파일러 소스나 오래된 PR뿐인 용어는 각주를 붙이거나 풀어 쓰기를 제안한다. 이미 확인한 것은 노트의 "용어 출처" 절에 있다.

### 3) 문장·맞춤법

여기까지 오면 직접 다듬는다. 허용 범위는 문장 단위다.

- 맞춤법·띄어쓰기·조사
- 문장 분리·병합, 어순
- 중복 표현 제거

**내용을 더하거나 빼지 않는다.** 문단을 새로 쓰거나 주장을 추가하는 것은 제안으로만 낸다. 사용자가 쓴 목소리를 유지한다.

코드 블록·에러 메시지·타입 이름·표의 셀 값은 한 글자도 바꾸지 않는다. 다듬은 뒤 코드 블록이 바이트 동일한지 확인한다.

`humanize-korean` 같은 AI 티 제거 도구는 **기본으로 돌리지 않는다.** 사람이 쓴 글이다. 사용자가 명시적으로 요청할 때만 쓴다.

## 발행

`publish` 같은 발행 플래그는 AI가 켜지 않는다. 검토가 끝났다고 알리고 발행은 사용자에게 맡긴다.

## 공통 규칙

- 값은 제시 전에 실측한다. 검증 없이 "아마 이렇게 된다"를 쓰지 않는다.
- 코드 블록은 원본 축자다. 변형·값 대입 금지.
- 개요·검토 결과에서 과거 사실을 번호(`3절의 X2`, `Unit 1 사실 목록`)로 참조하지 않는다. 인용할 사실은 그 자리에 코드 한두 줄로 다시 쓴다. 터미널 대화에는 되돌아볼 목차가 없다.
- 1인칭 오답 서사를 쓰지 않는다. 학습 중 틀린 것을 글의 소재로 삼지 않는다. 개념 정리가 목적이다.
